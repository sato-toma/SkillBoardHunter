# SkillBoard Hunter 開発計画

## 1. 目的

SkillBoard Hunterは、自分が持っているスキルや、これから身につけたいスキルを可視化するためのアプリケーション。

将来的には、現在のスキルから目標までに必要なスキルを発見したり、他人のSkill Boardから新しいスキルや成長経路を見つけられるようにする。

### コンセプト

> **自分に必要なSkillを探す。**

---

## 2. 基本機能

### Skill

* Skillを登録する
* Skillの説明を登録する
* Skillの習熟度を設定する
* Skillに経験や成果物を紐付ける

### Goal

* 将来達成したい目標を登録する
* Goalに必要なSkillを定義する
* SkillからGoalまでの経路を表示する

### Skill Graph

* Skill同士の関係を表現する
* Skillをグラフとして可視化する
* 現在のSkillからGoalまでの経路を探索する
* 目標までの「あと何手」を表示する

### Sharing

* Skill BoardをExport / Importできるようにする
* 他人のSkill Boardを閲覧できるようにする
* 他人のSkillを自分のBoardへ取り込めるようにする

---

## 3. 開発方針

### Local First

* 基本的な機能は端末だけで利用できるようにする
* 中央サーバーを必須にしない
* オフラインでも利用できる構成を目指す

### User Owned Data

* ユーザー自身がデータを管理できるようにする
* 特定サービスへの依存を避ける
* 人間が読める形式でデータを保存する

### Server Optional

* 初期段階ではサーバーを持たない
* オンライン機能が必要になった場合のみサーバーを導入する

### Progressive Development

* 最小限の機能から開発する
* 必要性が確認できた機能から段階的に追加する
* 初期段階では複雑なGraph探索やP2P通信を実装しない

### MVP-1 UX structure: workspace navigation

Skill Board、Quest、Goal、Evidenceの閲覧と編集を同じ画面に積み上げず、共通のワークスペース枠の中でビューを分ける。

採用する構成:

* デスクトップは左側の固定ナビゲーションで `Map`、`Quests`、`Goals` を切り替える
* モバイルは左パネルを下部ナビゲーションへ置き換える
* `Map` は現在地、未知の領域、次に開くSkillを確認する主画面とする
* `Map` はノードの編集を行わず、閲覧、選択、ズーム、パンを中心に扱う
* `Quests` と `Goals` は一覧・詳細の閲覧を中心にし、追加・編集は専用の作成/編集フローへ分ける
* Skillの詳細編集はMap上の選択パネル、またはSkill詳細ビューから行う
* どのビューからでも現在のGoal、選択中Skill、未完了Questへ戻れる
* 追加操作は最初に名前やタイトルだけを入力し、詳細は後から編集できる

この構成により、Mapをゲームの「現在地」として保ち、QuestやGoalの管理操作が成長体験を覆い隠さないようにする。左ナビは単なる設定メニューではなく、ユーザーが今どの視点で成長を見ているかを示す場所として扱う。

実装順:

1. 共通ワークスペース枠とルーティング可能なビュー状態を追加する
2. Mapを主画面として独立させる
3. Mapのズーム・パン操作を追加する。デスクトップではMiddle Mouseを第一候補とする
4. Questの閲覧ビューとQuest作成/編集フローを分離する
5. Goalの閲覧ビューとGoal作成/編集フローを分離する
6. EvidenceとLevel UpはQuest完了画面で確認できるようにし、独立した履歴ビューは作らない
7. Windows/Webで検証後、Android/iOS向けにナビゲーション操作を調整する

受け入れ条件:

* Map、Quests、Goalsをナビゲーションから切り替えられる
* ビューを切り替えても現在のGoalとSkillの状態が失われない
* 閲覧ビューから追加/編集フローへ明確に移動できる
* 追加フォームは最小入力で開始でき、詳細編集へ進める
* Mapは常に現在地と次に取れる行動を最初に見せる
* Mapを拡大・縮小してもノードと関係線を確認できる
* デスクトップとモバイルでナビゲーションが画面を圧迫しない

このUX構造はSkill、Goal、Quest、Evidenceを別概念として扱うための画面境界であり、データモデルや保存形式を変更するものではない。

### Map操作の将来計画

Mapは閲覧専用のため、ノードの追加・編集は行わない。ただし、広いグラフを確認するための表示操作は提供する。

* [ ] デスクトップでMiddle Mouseを使ったズームイン・ズームアウトの操作モデルを検証する
* [ ] ズーム中もノード選択や編集ページへの遷移を妨げない操作設計を確認する
* [ ] ズーム倍率の下限・上限、初期倍率、中心点の扱いを定義する
* [ ] Androidでpinch zoomとtouch dragを使う操作を検討する
* [ ] iOSでpinch zoomとtouch dragを使う操作を検討する
* [ ] マウス、タッチ、キーボード操作の共通フィードバックを検証する

第一候補はWindows/WebのMiddle Mouse操作とし、タッチ操作は将来のAndroid/iOS対応計画として扱う。タッチ操作の実装時期やジェスチャーの詳細は、実機検証で決定する。

### 今回の実装方針

MVP-1の最初の縦切りでは、Goalを起点にSkillを確認できる2Dボードを実装する。
Skillにはユーザー個人の経験値、そこから導出する習熟レベル、状態ラベルを持たせる。

### 将来計画: 多次元Skill Board

Skill Boardの2D表示は、Goal、Skill、Evidence、関係、時間、外部評価などの情報を
投影したビューとして扱う。将来は情報の次元が増えることを前提に、データモデルと
ビューを分離し、3D/4Dを含む別の表示方式へ置き換えられる構造を検討する。

* [ ] Goal / Skill / Evidence / Relation / 時系列を統合した次元中立のモデルを設計する
* [ ] 同じBoardデータから2D、3D、時間軸ビューを切り替えられるようにする
* [ ] ビューごとの投影ルールと情報密度を定義する
* [ ] 3D/4D表示の操作性とWindows・Android・iOS対応を検証する
* [ ] 他ユーザーから参照・評価された経験値を、個人の習熟度と分離して扱う

注記: TOMLのExport/Importは将来課題として扱い、初期の体験づくりを優先する。

## 6. データモデル

主要な概念：

* User
* Skill
* Goal
* SkillRelation
* Experience
* Evidence

特に以下を分離する。

* **Skill**：何ができるか
* **Experience**：何を経験したか
* **Evidence**：SkillやExperienceを示すもの
* **Goal**：これから達成したいこと

初期段階では必要最小限のデータモデルから開始する。

## 7. データ保存

```text

    ↓

    ↓
Export / Import
```

将来的にオンライン共有を追加しても、ローカルデータを失わない設計を目指す。

## 11. 最初のゴール

最初に目指すのは、Skill GraphやGoalまで完成させることではない。

まず、

> **「Skillを登録して、自分のSkillとして保存できる」**

という最小限の体験を成立させる。

そこから、

```text
Skillを登録する
    ↓
Skillを保存する
    ↓
Skillを編集する
    ↓
Skill同士をつなぐ
    ↓
Skill Graphを見る
    ↓
習得したいSkillを登録する
    ↓
Goalを設定する
    ↓
Goalまでの道を見る
```

と段階的に発展させる。
