# Development Workflow

SkillBoard Hunterの開発は、次のフェーズを分けて進める。前のフェーズの完了条件を満たすまで、次のフェーズの作業を開始しない。

## Phase 1: Plan

目的と優先順位を決める。

成果物:

- 対象とするユーザー価値
- MVPまたはIssueとの対応
- スコープと対象外
- 受け入れ条件の初案
- 未確定の仕様質問

完了条件:

- 何を作るか、何を作らないかが説明できる
- 未確定事項が質問として列挙されている
- 受け入れ条件がユーザー視点で確認可能になっている

## Phase 2: Change Scope

変更の影響範囲とリスクを確認する。

成果物:

- 変更対象のファイル、モジュール、データ
- 既存機能への影響
- 永続化形式や互換性への影響
- プラットフォーム差分
- 変更しない範囲
- 技術的課題の候補

完了条件:

- 変更範囲が列挙され、過剰な変更が除外されている
- 既存コードとテストの確認が済んでいる
- 破壊的変更や移行の要否が判断されている

## Phase 3: Detailed Design

実装方法とテスト方針を確定する。

成果物:

- `docs/detailed-design-template.md` に基づく詳細設計
- モジュール境界とデータフロー
- データモデル、バリデーション、エラー処理
- 単体テスト、機能テスト、手動確認の計画
- トレードオフと、必要ならADR

完了条件:

- 仕様の未解決事項が解消されている
- 実装者が追加のプロダクト判断なしに実装できる
- 各受け入れ条件に検証方法が紐づいている
- 設計変更が必要な場合はADRの要否が判断されている

## Phase 4: Implementation

承認済みの詳細設計に従ってコードを実装する。

成果物:

- プロダクションコード
- 必要な型、アダプター、UI、状態更新
- 設計との差分と、差分が生じた理由

完了条件:

- 実装が詳細設計と一致している、または差分が記録されている
- 単体テストを実行できる状態になっている
- 実装直後に型チェック、Lint、または最小のビルド確認を実行している

## Phase 5: Unit Test

関数、ドメインロジック、状態遷移、アダプターの単位で検証する。外部環境や実ブラウザへの依存は最小限にする。

確認対象:

- 正常系
- 境界値と不正入力
- 空データ
- エラー処理
- 状態遷移
- シリアライズと復元

完了条件:

- 設計で定義した単体テストが追加されている
- テストが再現可能なコマンドで成功している
- 失敗したテストや未検証のリスクが `docs/technical-issues.md` に記録されている

## Phase 6: Functional Test

ユーザーが実際に行う操作の流れとして検証する。単体テストでは確認できない画面、永続化、ルーティング、プラットフォーム境界を対象にする。

確認対象:

- 主要なユーザーフロー
- 受け入れ条件
- 画面表示、入力、操作結果
- 保存、再読み込み、復元
- エラー、空状態、ローディング状態
- 対象プラットフォームごとの差分

完了条件:

- すべての受け入れ条件に検証結果がある
- 機能テストのコマンド、手順、または実行環境が記録されている
- 未実施の確認と残存リスクが明記されている

## Phase Transition Rules

- 仕様が不明なままPhase 4へ進まない。
- Phase 2で永続化、公開API、またはアーキテクチャを変更すると分かった場合、Phase 3でADRの要否を判断する。
- Phase 4の実装とPhase 5の単体テストを、同じ変更として曖昧に報告しない。
- Phase 5の成功だけで機能完成と判断しない。Phase 6で受け入れ条件を確認する。
- 各フェーズの成果物と検証結果を、PRまたは作業サマリーに記録する。
